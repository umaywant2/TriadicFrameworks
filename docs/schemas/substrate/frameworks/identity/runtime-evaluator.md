---

# 🜁 **1. Hook Intake Layer**  
### *All evaluation begins with runtime hooks*

The evaluator receives raw substrate events from:

- execution hooks  
- atlas hooks  
- epoch hooks  
- coupling hooks  
- invariance hooks  
- monitor hooks  

These hooks form the **runtime telemetry stream**.

**Purpose:**  
Provide analyzers with the substrate’s real‑time behavior.

---

# 🜁 **2. Analyzer Dispatch Layer**  
### *Hooks are routed to analyzers based on relevance*

Each hook is dispatched to one or more analyzers:

- **Stability Analyzer** → resonance_shift, drift_spike  
- **Invariance Analyzer** → invariance_break, invariance_restore  
- **Epoch Analyzer** → epoch_transition, propagation_cycle  
- **Coupling Analyzer** → resonance_surge, coupling_instability  
- **Continuity Analyzer** → sync_event, cycle_report  
- **Telemetry Analyzer** → telemetry_packet, anomaly_alert  

**Purpose:**  
Ensure each analyzer receives only the hooks it is designed to interpret.

---

# 🜁 **3. Operator Application Layer**  
### *Analyzers apply RTT operators to interpret hook data*

Each analyzer uses its operator set:

- **Lumen** → structure, influence, pressure, continuity  
- **Hephaestus** → regime classification  
- **Aurion** → topology, ancestry, collapse detection  
- **Harmonia** → triadic synthesis, resonance scoring  

**Purpose:**  
Transform raw hook data into structured triadic meaning.

---

# 🜁 **4. Layer Evaluation Stage**  
### *Operators feed into RTT layers*

Each analyzer evaluates one or more layers:

- **Resonance Layer**  
- **Continuity Layer**  
- **Drift Layer**  
- **Coherence Layer**  
- **Epoch Layer**  
- **Coupling Layer**  
- **Dimensional Layer**  
- **Regime Layer**  
- **Cross‑Cutting Layer**  
- **Monitor Layer**

**Purpose:**  
Convert operator outputs into layer‑level triadic assessments.

---

# 🜁 **5. Triadic Synthesis Stage**  
### *All layer evaluations are blended into triadic signatures*

Using Harmonia operators, the evaluator produces:

- **drift signature**  
- **coherence signature**  
- **stability signature**

These signatures are combined into a **triadic profile** for each engine and epoch.

**Purpose:**  
Create a unified triadic identity for the runtime state.

---

# 🜁 **6. Constellation Integration Stage**  
### *Triadic profiles are mapped onto the runtime graph*

Using:

- `runtime-graph.md`  
- `runtime-graph.extended.json`  

The evaluator integrates triadic profiles across:

- flow edges  
- feedback edges  
- weights  
- phases  
- triadic signatures  

**Purpose:**  
Understand how each engine affects the others.

Provide the substrate with its current triadic identity.
